This table is generated from the runtime trigger vocabulary. It describes the XML `type` values in a playbook, not the different JSON shape used by the agent-library provisioner.

| Type | Fires when | Required trigger attributes | Dispatch |
| --- | --- | --- | --- |
| `any` | every supported event — email, meeting, Slack message, LinkedIn message, accepted LinkedIn connection, external-CRM sync (calendar changes, signals, calls, texts and custom events require explicit opt-in) | None beyond type | orchestrator |
| `email` | an inbound or outbound email | None beyond type | orchestrator |
| `meeting` | a meeting, once its transcript has landed | None beyond type | orchestrator |
| `calendar` | A linked calendar event is created, updated or cancelled | None beyond type | orchestrator |
| `slack` | a message in a linked Slack channel | None beyond type | orchestrator |
| `linkedin` | a LinkedIn message the counterpart sent (with any of the user's own alongside) — the user's sends alone never fire it | None beyond type | orchestrator |
| `linkedin_connection` | someone accepting a LinkedIn connection request the user sent | None beyond type | orchestrator |
| `external_crm` | a deal changing in the connected CRM (the sync, not a Cedar field write) | None beyond type | orchestrator |
| `call` | A deal call logged with playbook processing enabled | None beyond type | direct |
| `text` | A deal text logged with playbook processing enabled | None beyond type | direct |
| `custom` | A published organization event is submitted for playbook processing | `eventKey` (published key or `*`) | direct |
| `signal` | an actionable CRM signal, including watcher discoveries and qualified email-open evidence | None beyond type | direct |
| `field-change` | a Cedar field taking a value — the only trigger that fires exactly once, when the thing becomes true | `field`, `to-value` | direct |
| `cron` | a schedule, independent of any event | `schedule`, `timezone` | direct |
| `before-meeting` | N minutes before a calendar event, if the meeting is already in the calendar data Cedar holds | `minutes` | direct |
| `webhook` | an external POST to the playbook webhook endpoint, or a registered Slack-channel source | `id` | direct |

## How dispatch differs

Orchestrator triggers pass relevant instructions and agent descriptions to the event orchestrator, which decides which referenced agents to run. Direct triggers dispatch the configured block's referenced agents through their supported execution path.

A supported trigger still needs a saved agent document, a valid document reference, compatible scope and the required connection. Calendar changes and signals require explicit opt-in rather than being implied by `any`. A before-meeting trigger needs calendar data Cedar already holds. ## Conditions on a trigger

Every playbook trigger can have a filter, a Jev question, or both. Add the condition to the trigger block in the editor, or use MCP to edit that block in the playbook. Cedar first matches the trigger as usual. It then checks the filter once for the block. If the filter passes, Jev evaluates the question using the context selected for that block. Each matching block makes its own decision.

A false filter skips the block. Missing required evidence holds it. A scheduled or webhook run can have no deal, so only request deal context when the rule requires one. A condition on **Any** keeps its existing event coverage. A condition on **Signal** controls the agents that respond to an actionable signal. Cedar still records the signal when the block skips.

Use **Custom** for events your own system sends to Cedar. Publish an event key, send the occurrence, and choose that key in the playbook. **Signal** is for actionable signals produced by Cedar’s watcher and native signal paths. [Custom event intake](/integrations/custom-crm-data#run-a-playbook-when-an-event-arrives).

### Context sources for a Jev question

In the trigger editor, select **Add source** to choose what Jev reads when it evaluates your question. You can combine up to 10 selections. When editing through MCP, use the source keys below.

| Source | What Jev can read | Requires a deal? |
| --- | --- | --- |
| `event` | The triggering event, including its payload when available. | No |
| `participants` | The participants supplied by the event or by the trigger when it runs. | No |
| `deal` | The deal’s name, stage, and creation date. | Yes |
| `summary` | The deal’s saved status overview and next steps. | Yes |
| `recent_activity` | The user’s most recent events on this deal, including type, title, summary, and time. Set `limit` to 1–20 events and `daysBack` to 1–90 days. | Yes |
| `related_tasks` | The user’s most recently created tasks on this deal, including description, status, and due date. Set `limit` to 1–20 tasks. | Yes |
| `file` | The title and contents of an accessible Cedar document. Supply its UUID as `documentId`. | No |

For example, to ask “Does this event meet the criteria in our qualification guide?”, select `event` and `file`, then choose the guide by document ID. Add `summary` if the answer also depends on the deal’s next steps. If a webhook fires without a deal, selecting `summary` puts that block on hold. The same applies when another selected source is unavailable, such as a file the user cannot access.
