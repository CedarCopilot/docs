## Complete metric catalog

These **22 metrics** come from `describe-metrics`. Each metric defines its reducer, unit and supported dimensions; arbitrary combinations are not supported.

| Metric | Capability | Reduction / unit | Group by | Requirements |
| --- | --- | --- | --- | --- |
| `response_time` | Median seconds between consecutive direction-changing events (their reply latency). | median / seconds | `rep`, `stage`, `deal`, `event_type`, `email_classification`, `outcome`, `month` | See description and input contract |
| `followup_time` | Median seconds between consecutive outbound emails (follow-up cadence). | median / seconds | `rep`, `stage`, `deal`, `event_type`, `email_classification`, `outcome`, `month` | See description and input contract |
| `post_meeting_time` | Median seconds from a meeting to the next email (post-meeting recap latency). | median / seconds | `rep`, `stage`, `deal`, `event_type`, `email_classification`, `outcome`, `month` | See description and input contract |
| `reply_rate` | Share of deals (with an outbound email) that drew an inbound reply. | rate / percent | `rep`, `deal`, `outcome`, `month` | See description and input contract |
| `event_count` | Number of events matching the filter (activity volume). | count / count | `rep`, `stage`, `deal`, `event_type`, `email_classification`, `outcome`, `month` | See description and input contract |
| `stage_funnel` | Funnel — count of DISTINCT deals that reached each stage (a deal reached stage X if any of its events is stamped stage_at_time=X). Groups by stage; ignores groupBy. | count / count | No grouping | See description and input contract |
| `time_between_stages` | Median seconds each deal took to move from stageA to stageB (target="stageA-&gt;stageB"). | median / seconds | `rep`, `deal`, `outcome`, `month` | target |
| `win_rate` | Share of terminal deals that were won — requires the outcome mapping. | rate / percent | `rep`, `deal`, `outcome`, `month` | outcome |
| `aop_conversion` | Lead-band: share of conversations ever bound to a non-Deal AOP that were later reassigned to a Deal-bound AOP (a real AOP change, e.g. Vooma's Lead AOP → Deals AOP at qualification) — "lead → opp conversion". Deals-only conversations (never non-Deal-bound) are excluded, same as win_rate excludes non-terminal deals. No outcome mapping needed — the AOP's own boundObjectApiName is the terminal signal, not a status value. | rate / percent | `rep`, `deal`, `month` | See description and input contract |
| `deals_dropped` | Share of OPEN deals (requires outcome) whose last outbound touch (email or meeting) is older than target days (default 10) — a never-contacted deal always counts as dropped. | rate / percent | `rep`, `deal`, `month` | outcome |
| `quiet_gap` | Median days since the last outbound touch, over OPEN deals (requires outcome) that have EVER been touched — never-contacted deals are excluded (see deals_dropped for that fact). target is unused (the day-threshold only gates deals_dropped/gave_up_count). | median / days | `rep`, `deal`, `month` | outcome |
| `gave_up_count` | Average number of outbound emails in a stalled, unanswered chain — a run of outbound sends since the last inbound reply (or ever, if none) whose last send is at least target days old (default 10). No outcome mapping needed. | mean / count | `rep`, `deal`, `month` | See description and input contract |
| `hygiene` | Average COUNT of populated fields on the OPEN pipeline (requires outcome, redefined 2026-09-29): the 4 native buyer fields (company, contact, deal_value, next_step — target optionally narrows this subset, default all four) PLUS every custom field that deal's own rep has actually live-synced from their CRM (resolved per rep, not a fixed list — see queryHygieneSamples). A raw count, not a percentage: the real denominator varies per rep. | mean / count | `rep`, `deal`, `month` | outcome |
| `contacts_reached` | Median distinct REAL external contacts per deal in the OPEN pipeline (requires outcome, redefined 2026-09-29), from crm_conversation_contacts — excludes the org's own staff (its configured domains) and known automated/vendor senders (a calendar-notification alias, a document-signing relay, a sales-engagement tool, etc.); a real contact on a personal email domain still counts. A deal with no qualifying contact is a real 0, not omitted. | median / count | `rep`, `deal`, `month` | outcome |
| `open_deal_age` | Median days since the earliest tracked event on each OPEN deal (requires outcome) — a live snapshot of pipeline staleness, not historical time-to-close. Replaces time_between_stages as deal_progression's real source: that one needs a stageA-&gt;stageB target this schema has nowhere to carry, and even with one only ~23% of closed deals at a real org had a usable stage-transition timestamp. A deal with no tracked event at all has no computable age and is excluded, not counted as 0. | median / days | `rep`, `deal`, `month` | outcome |
| `stalled_deal_revenue` | Real SUM of deal_value across OPEN deals quiet past the quiet-gap threshold (requires outcome; target is an optional day-threshold override, default 10, same convention as deals_dropped/quiet_gap/gave_up_count) — the same stalled-deal population as deals_dropped, summed by dollar value instead of counted. A stalled deal with no deal_value contributes 0, not excluded. | sum / currency | `rep`, `deal`, `month` | outcome |
| `crm_won_amount` | Live CRM closed-won amount and count by currency in an explicit close-date window. Requires exactly one filter.reps user, from/to, and crmReporting.timezone. Uses mapped ACV and provider closed flags; no Cedar fallback. Includes verified provider deal inventory and missing-amount count. | sum / currency | No grouping | See description and input contract |
| `crm_open_due_amount` | Live CRM open amount and count by currency closing in an explicit window. Same required rep/window/timezone and verified inventory as crm_won_amount; no Cedar fallback. | sum / currency | No grouping | See description and input contract |
| `total_pipeline` | Real SUM of deal_value across OPEN deals that actually have one (requires outcome) — the performance report's former headline "total pipeline" figure (superseded by won_pipeline/avg_acv as the headline tile, 2026-09-30, but still real and independently useful). A deal with no positive deal_value is EXCLUDED, not zero-filled: unlike stalled_deal_revenue, this can't legitimately count a dollar figure nobody has. | sum / currency | `rep`, `deal`, `month` | outcome |
| `won_pipeline` | Total dollar value of CLOSED-WON deals in the window (requires outcome), summing deal_value over deals with a real (non-null, non-zero) deal_value. Shares its sample set with avg_acv (same deals, reduced via sum instead of mean). | sum / currency | `rep`, `deal`, `month` | outcome |
| `avg_acv` | Average deal_value across CLOSED-WON deals in the window (requires outcome), over deals with a real (non-null, non-zero) deal_value. Shares its sample set with won_pipeline (same deals, reduced via mean instead of sum). | mean / currency | `rep`, `deal`, `month` | outcome |
| `judged_strength` | Average taxonomy-atom strength across every list-field atom whose field_id matches target (a family glob, e.g. "coaching.discovery.*" or "coaching.followup.rs*") — the ONE metric that aggregates the sub-event taxonomy rather than crm_conversations/crm_events. Atoms with no strength score are excluded, never counted as 0. No outcome mapping needed. | mean / score | `rep`, `deal`, `month` | target |

### Reporting semantics

- This catalog covers EVENT and DEAL metrics, plus ONE taxonomy-ATOM metric: "judged_strength" (average strength across every list-field atom whose field_id matches a target family glob, grouped by rep/deal/month and windowed by date like any other metric here). What is still NOT here: per-criterion distributions, counting occurrences, or aggregating a non-strength payload key — those still need `run-sql`, which also gives readable rep names and arbitrary per-deal normalization this catalog never will. Start with the `taxonomy-fields` tool to learn which fields exist, then load-skill("run-sql") for anything "judged_strength" cannot express.
- Every row returns &#123; group, value, n, sampleIds &#125; — n is the sample size, sampleIds (capped at 50) point back to the atoms/events summarized.
- groupBy:"outcome" and metric "win_rate" both REQUIRE an agent-supplied outcome:&#123; won:&#91;...&#93;, lost:&#91;...&#93; &#125; status mapping.
- The filter is the SAME TimelineFilter cube used by the timeline reader; omit conversationIds to scope org-wide.
- response_time/followup_time/post_meeting_time/reply_rate/event_count/stage_funnel/time_between_stages already generalize to any AOP as-is — none hardcodes an Opportunity-specific stage/status literal; stage and status vocab are always caller-supplied or read off the AOP's own field definitions. "win_rate" generalizes the same way (see its own note). "aop_conversion" is the one genuinely new Lead-band metric — an AOP reassignment is not a status value on any single AOP's vocabulary.
- "deals_dropped"/"quiet_gap"/"gave_up_count" share one `target` convention: an optional positive number of days (the quiet-gap threshold), defaulting to 10 when omitted. "hygiene"'s `target` is unrelated — an optional comma-separated subset of its field keys (company, contact, deal_value, next_step), defaulting to all four.

Live CRM amounts require one explicit rep, a close-date window and reporting timezone. Their verified inventory and per-currency totals differ from Cedar's stored deal metrics. [Reporting workflow](/crm/metrics).

## conversation-analytics

Availability: **external**. [Parameters and responses](/reference/conversation-analytics).

<Accordion title="Full tool behavior and constraints">

Compute cadence, funnel and pipeline metrics server-side; never tally rows yourself. Use describe-metrics for the metric/groupBy catalog, reducers, units and requirements. ACTIONS: compute-metric with computeMetric:&#123;metric,filter,...&#125;; compute-metric-batch with computeMetricBatch:&#123;items:&#91;&#123;id,metric,filter,...&#125;&#93;&#125; (up to 50 isolated items); describe-metrics. The shared filter cube supports conversationIds, reps, stages and date bounds; omitted conversationIds means org-wide. Rows include value,n,sampleIds; ordinary n:0 becomes null. Live-only crm_won_amount/crm_open_due_amount require filter.reps:&#91;one Cedar user ID&#93;, explicit from/to date bounds and crmReporting:&#123;timezone:IANA zone&#125;. They use provider close dates and mapped amounts, never fall back to Cedar, and separate currencies. Results include verifiedAt and crmDeals with exact Cedar conversation IDs when linked. Verified empty windows return 0; missing amounts return null with knownAmountSubtotal and missingAmountCount. Call live metrics sequentially to respect CRM rate limits. Cedar win_rate/deals_dropped/quiet_gap/hygiene/won_pipeline/avg_acv and groupBy:outcome require outcome:&#123;won,lost&#125;; inspect conversation-read describe-field for status vocabulary. Cedar does not infer terminal status. judged_strength averages taxonomy atom strength for a target field-family glob such as coaching.discovery.*. Other taxonomy counts/distributions and payload aggregations use run-sql; discover available fields with taxonomy-fields.

</Accordion>

### Supported operations

| Operation | Capability | Baseline scope |
| --- | --- | --- |
| `compute-metric` | Compute one supported pipeline, cadence, hygiene, revenue or evidence metric. | `crm:read` |
| `compute-metric-batch` | Compute several supported metric requests in one call. | `crm:read` |
| `describe-metrics` | Discover supported metric definitions and their inputs before choosing an analysis. | `crm:read` |
