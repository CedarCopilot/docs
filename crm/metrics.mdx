Call `conversation-analytics describe-metrics` to retrieve the runtime metric catalog, supported groupings, units and requirements.

```json
{ "action": "describe-metrics", "describeMetrics": {} }
```

## Metric families

| Area | Metrics |
| --- | --- |
| Live external CRM amounts | `crm_won_amount`, `crm_open_due_amount` |
| Response and follow-up cadence | `response_time`, `followup_time`, `post_meeting_time`, `reply_rate`, `event_count` |
| Funnel movement | `time_between_stages`, `stage_funnel`, `win_rate`, `aop_conversion`, `deals_dropped` |
| Pipeline hygiene | `quiet_gap`, `gave_up_count`, `hygiene`, `contacts_reached`, `open_deal_age` |
| Revenue | `stalled_deal_revenue`, `total_pipeline`, `won_pipeline`, `avg_acv` |
| Extracted coaching/qualification | `judged_strength` |

Use `compute-metric` for one question or `compute-metric-batch` for up to 50 independently identified items. Batch item IDs map results back to the question; do not rely on array order. Trend items can expand into consecutive week/month windows.

## Cohorts and denominators

Filters can restrict deals, reps, stages, dates and supported evidence dimensions. Omitting conversation IDs can widen the query to the organization. Pick the cohort deliberately. Rows return `value`, sample count `n`, and sample IDs; report these when explaining a result. Sample IDs are capped at 50 and need not enumerate the full sample. Preserve the returned empty/missing state instead of inventing a zero. See [visibility and statistical backing](/intelligence/statistical-backing) for sampling units, denominators, normalization, provenance and statistical interpretation.

Outcome-sensitive Cedar metrics require an explicit `outcome` definition with the account's won/lost values. Cedar does not infer which custom statuses are terminal. `judged_strength` requires the intended taxonomy family in `target`.

## Live CRM reporting

Live amount metrics require exactly one rep, explicit date bounds and an IANA reporting timezone. They use the provider's close dates and mapped amounts, return verification/provenance information, and keep currencies separate. They do not silently substitute Cedar values if the provider is unavailable.

A verified empty live window can be zero; missing amounts yield null with known subtotal and missing-amount counts. Call live metrics sequentially to respect the provider's rate limits.

### Reporting semantics

- This catalog covers EVENT and DEAL metrics, plus ONE taxonomy-ATOM metric: "judged_strength" (average strength across every list-field atom whose field_id matches a target family glob, grouped by rep/deal/month and windowed by date like any other metric here). What is still NOT here: per-criterion distributions, counting occurrences, or aggregating a non-strength payload key — those still need `run-sql`, which also gives readable rep names and arbitrary per-deal normalization this catalog never will. Start with the `taxonomy-fields` tool to learn which fields exist, then load-skill("run-sql") for anything "judged_strength" cannot express.
- Every row returns &#123; group, value, n, sampleIds &#125; — n is the sample size, sampleIds (capped at 50) point back to the atoms/events summarized.
- groupBy:"outcome" and metric "win_rate" both REQUIRE an agent-supplied outcome:&#123; won:&#91;...&#93;, lost:&#91;...&#93; &#125; status mapping.
- The filter is the SAME TimelineFilter cube used by the timeline reader; omit conversationIds to scope org-wide.
- response_time/followup_time/post_meeting_time/reply_rate/event_count/stage_funnel/time_between_stages already generalize to any AOP as-is — none hardcodes an Opportunity-specific stage/status literal; stage and status vocab are always caller-supplied or read off the AOP's own field definitions. "win_rate" generalizes the same way (see its own note). "aop_conversion" is the one genuinely new Lead-band metric — an AOP reassignment is not a status value on any single AOP's vocabulary.
- "deals_dropped"/"quiet_gap"/"gave_up_count" share one `target` convention: an optional positive number of days (the quiet-gap threshold), defaulting to 10 when omitted. "hygiene"'s `target` is unrelated — an optional comma-separated subset of its field keys (company, contact, deal_value, next_step), defaulting to all four.

Live CRM amounts require one explicit rep, a close-date window and reporting timezone. Their verified inventory and per-currency totals differ from Cedar's stored deal metrics. [Reporting workflow](/crm/metrics).
