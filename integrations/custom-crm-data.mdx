title: "Send custom CRM events"
description: "Publish an event contract, send a typed occurrence, verify its receipt, and retry safely."

Use this guide once your workspace has the custom CRM data release. An organization owner or admin publishes a versioned contract in Cedar. A customer connection can then send occurrences to that workspace. Each occurrence has an external ID, timestamp, typed payload and named links to Cedar account or contact IDs. Store these IDs in your sender before delivery. A domain, email address, Salesforce ID or warehouse row ID cannot stand in for a Cedar record ID.

### Set up website visits with a coding agent

Once your workspace has the self-service MCP release, connect your coding agent to [Cedar MCP](/getting-started/quickstart) as a workspace owner or admin. Grant `crm:read`, `crm:write` and `crm:manage`. Reauthorize an existing connection to add the setup permission. Tell the agent:

> Set up website visits in Cedar. Reuse a compatible website_visit definition, or publish it if missing. For my first identified visit, find or create the visiting company's account by domain. If the source identified the visitor by email, link their contact too. Use the source ID and timestamp to record the visit, then verify it in the account's activity. Tell me whether recurring delivery is connected.

The agent can publish the definition before you have a visit. For verification, give it one real source row with a stable occurrence ID, timestamp, page path and the **visiting company's domain**. For an anonymous visit without a known company, wait for attribution. Use the visitor's email only when supplied by your source. The website being visited usually belongs to you.

The agent uses `conversation-read` to discover the current contract, then `crm-write` to publish a missing definition:

```json
{
  "action": "publish-event-definition",
  "user_request_summary": "Set up website visits in Cedar",
  "is_new_request": true,
  "publishEventDefinition": {
    "eventKey": "website_visit",
    "expectedPreviousVersion": 0,
    "label": "Website visit",
    "payloadSchema": [{"name": "path", "type": "string", "required": true}],
    "entityLinks": [
      {"name": "visitor_account", "kind": "account", "required": true, "cardinality": "one"},
      {"name": "visitor", "kind": "contact", "required": false, "cardinality": "one"}
    ]
  }
}
```

For an identified visit the agent uses `ensure-record` for the workspace account and optional contact, passes those Cedar IDs to `create-event`, and reads `conversation-read` → `record-profile` with `activity: {}`. An unchanged retry under the same sender should return the same event ID. If a definition already exists with different fields, review its version and the impact on existing senders before publishing an update. [CRM write actions](/reference/crm-write)

**Continuous delivery** starts when your analytics backend sends new visits. Its OAuth connection needs its own `crm:write` grant. Keep the token on the server. A verified sample confirms the Cedar setup; use the sender example below to connect your source.

### Choose an event

These examples use synthetic data. Choose the event key and replace the sample values with values from your source. The payload field names below are illustrative Cedar contract names. Your sender translates its source columns into that contract.

| Source observation | Event key | Payload example | Named links |
| --- | --- | --- | --- |
| An integration was connected in the product | `product_activity` | `{"activity":"integration_connected"}` | Required account `customer_account` |
| A champion changed employers | `job_change` | `{"position":"VP Operations"}` | Required account `new_employer` and contact `champion` |
| A visitor opened the pricing page | `website_visit` | `{"path":"/pricing"}` | Required account `visitor_account`, optional contact `visitor` |
| An account showed intent for a topic | `intent_observed` | `{"topic":"fleet software","score":84}` | Required account `interested_account` |

### Publish through the admin API

Use an authenticated administrator session for the tRPC mutation `POST /api/trpc/crm.eventDefinitions.publish`. The inbound OAuth token is for submitting occurrences. To publish without exporting your session cookie, open Cedar while signed in as an organization owner or admin, open the browser developer console, and run this example. Set `apiOrigin` to the origin Cedar uses for its own `/api/trpc` requests, visible in the Network panel. Choose one event key per run.

```js
const apiOrigin = "https://YOUR-CEDAR-API-HOST";
const eventKey = "website_visit";
const examples = {
  product_activity: {
    label: "Product activity", fields: {activity: "string"},
    account: "customer_account",
  },
  job_change: {
    label: "Job change", fields: {position: "string"},
    account: "new_employer", contact: "champion", requireContact: true,
  },
  website_visit: {
    label: "Website visit", fields: {path: "string"},
    account: "visitor_account", contact: "visitor", requireContact: false,
  },
  intent_observed: {
    label: "Intent observed", fields: {topic: "string", score: "number"},
    account: "interested_account",
  },
};
const spec = examples[eventKey];
const definition = {
  eventKey, label: spec.label, expectedPreviousVersion: 0,
  description: "",
  payloadSchema: Object.entries(spec.fields).map(([name, type]) => ({
    name, type, required: true,
  })),
  entityLinks: [
    {name: spec.account, kind: "account", required: true, cardinality: "one"},
    ...(spec.contact ? [{
      name: spec.contact, kind: "contact",
      required: spec.requireContact, cardinality: "one",
    }] : []),
  ],
};
const response = await fetch(apiOrigin + "/api/trpc/crm.eventDefinitions.publish", {
  method: "POST", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({json: definition}),
});
const result = await response.json();
if (!response.ok) throw new Error(result.error?.json?.message || "Publish failed");
console.log(result.result.data.json);
```

Use `expectedPreviousVersion: 0` for a new event. A successful publish returns the definition and its version. If the key already exists, read it with the MCP `conversation-read` action `definitions`. To publish a revision, supply the version you reviewed as `expectedPreviousVersion`. [Definition discovery](/reference/conversation-read).

### Send a test occurrence

For a scheduled sender, ask Cedar to record your workspace admin's approval for `crm:write` on the service account. Exchange its client ID and secret for a bearer using the token request in the [service account guide](/integrations/export-conversations#service-account-for-a-scheduled-export), changing the scope to `crm:write`. Export and ingestion jobs can request separate tokens from the same client. Use the ingestion token as `CEDAR_ACCESS_TOKEN` in the example below. The same grant works for supported source-maintained list fields.

Use a connection with an explicit `crm:write` OAuth grant belonging to an authorized owner or admin. Set `CEDAR_API_ORIGIN`, `CEDAR_ORG_ID`, `CEDAR_ACCOUNT_ID` and `CEDAR_EVENT_KEY` in your shell. Provide `CEDAR_ACCESS_TOKEN` through your development environment’s secret manager. For `job_change`, also set `CEDAR_CONTACT_ID` to the champion’s Cedar contact ID. For `website_visit`, set it only when the source identifies a person. Set `CEDAR_EVENT_VERSION` to the version returned by publication.

The Python example uses only the standard library. Save it as `send_event.py` and run `python3 send_event.py`. Change the ID and timestamp when sending a distinct occurrence.

```python
import json
import os
from urllib.error import HTTPError
from urllib.request import Request, urlopen

env = os.environ
key = env["CEDAR_EVENT_KEY"]
account_link, contact_link, payload = {
    "product_activity": ("customer_account", None, {"activity": "integration_connected"}),
    "job_change": ("new_employer", "champion", {"position": "VP Operations"}),
    "website_visit": ("visitor_account", "visitor", {"path": "/pricing"}),
    "intent_observed": ("interested_account", None, {"topic": "fleet software", "score": 84}),
}[key]
links = {account_link: env["CEDAR_ACCOUNT_ID"]}
if key == "job_change":
    links[contact_link] = env["CEDAR_CONTACT_ID"]
elif contact_link and env.get("CEDAR_CONTACT_ID"):
    links[contact_link] = env["CEDAR_CONTACT_ID"]
body = {
    "kind": "event",
    "data": {
        "eventKey": key,
        "version": int(env["CEDAR_EVENT_VERSION"]),
        "externalEventId": f"example-{key}-001",
        "occurredAt": "2026-11-21T12:00:00Z",
        "payload": payload,
        "entityLinks": links,
    },
}
url = env["CEDAR_API_ORIGIN"].rstrip("/") + "/webhooks/custom-data/" + env["CEDAR_ORG_ID"]
request = Request(url, method="POST", data=json.dumps(body).encode(), headers={
    "Content-Type": "application/json",
    "Authorization": "Bearer " + env["CEDAR_ACCESS_TOKEN"],
})
try:
    with urlopen(request) as response:
        print(response.status, response.read().decode())
except HTTPError as error:
    print(error.code, error.read().decode())
    raise SystemExit(1)
```

The first successful call returns `201`, `created`, and a Cedar event ID. Repeat the same body under the same connector and user. Expect `200`, `replayed`, and the same ID. Keep `externalEventId` unique across all event types for that source. Cedar returns `409` when a retry changes the occurrence, `400` for undeclared payload fields and `412` for a required native record it cannot resolve. Check the error before retrying.

When an accessible deal already links to the same account or contact, read its `related-activity` through `conversation-read` and look for the returned event ID. That occurrence stays organization-owned and can surface on multiple related deals. [Deal activity lookup](/reference/conversation-read).

### Run a playbook when an event arrives

In the attached deal playbook, add **On event → Custom** and select the published event key. Choose **Any custom event** to match all published keys. Add the agents and optional conditions to that block.

The webhook saves each new event by default. Set `triggerPlaybook` at the top level of the request body, alongside `"kind": "event"`.

| What you are sending | What to pass | What Cedar does |
| --- | --- | --- |
| A live stream of new events that should trigger automation | `"triggerPlaybook": true` | Saves the event and requests background processing for matching deal playbooks. |
| A historical backfill or import | `"triggerPlaybook": false` | Saves the event without starting a playbook. Omitting the flag has the same effect. |

Choose the setting on the first submission. Resending a backfilled occurrence with `true` later returns its existing receipt and does not start a run.

Cedar checks conversations linked through the event’s accounts or contacts. Each eligible deal with a matching attached playbook can run once for this occurrence, even when several links lead to that deal. With no qualifying deal, the event is still saved. Repeating the same submission does not start another run. [Playbook triggers](/agent-platform/triggers).

### Release scope

The receiver accepts the Cedar contract directly. Triggering a custom outbound webhook from an incoming event is coming soon. For this release, map source records to the published contract before sending them. Source-maintained **list** attributes support appending observations. Scalar attribute writes are held for this release. [Custom fields and list values](/configuration/fields).
