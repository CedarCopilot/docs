## Capabilities

[Playbooks and triggers overview](/automation/playbooks) · [Complete capabilities](/capabilities/playbooks).

<Accordion title="Full tool behavior and constraints">

For "why didn't X happen"/system-behavior questions, load-skill('cedar-configuration') first. ACTIONS: (1) create-aop — create a new AOP/playbook cloned from an existing one (field definitions, display config, and the whole PLAYBOOK.md/resources/subagents document tree). cloneFromAopId is required; there is no from-scratch path. (2) update-selection-procedure — replace an AOP's routing text in full (the text an LLM classifier reads to decide which AOP a new conversation belongs to). Already readable via config-read's read-playbook (mode: "list"). (3) update-custom-assignment-instruction — replace (or, with null, clear) an AOP's free-text override for domain/company identification on its deals, taking precedence over the model's own judgment. Each action takes its params in a same-named object (e.g. action: "create-aop" pairs with a createAop: &#123;...&#125; object) — omit the others. For custom field definitions/options and their CRM mappings use config-write. For a connected integration's own config use connection-write.

</Accordion>

## Operations and scopes

| Action | Capability | Baseline scope |
| --- | --- | --- |
| `create-aop` | Create an AOP from an existing source configuration. | `playbook:write` |
| `update-selection-procedure` | Change the instructions used to select the appropriate AOP. | `playbook:write` |
| `update-custom-assignment-instruction` | Change the supported custom conversation-assignment instruction. | `playbook:write` |

Path, account role, feature gates, target ownership, and billing permissions can impose additional requirements.

## Supported options and filters

Every finite input choice is listed here, including array values and nested variants. Free-text filters, dates, numeric ranges and runtime validation are covered in the [parameter tables](/reference/aop-write#parameters). Options apply to their named operation or branch.

| Input | Choices | Variant / meaning |
| --- | --- | --- |
| `createAop.scope` | `user`, `org` | Conversation ownership scope: "user" (one conversation per user+company) or "org" (one shared conversation per org+company). Defaults to the source AOP's own scope. |
| `updateSelectionProcedure.scope` | `user`, `org` | Field owner: user AOP or linked org AOP. list-fields returns both; CRM mappings stay user-scoped. |
| `updateCustomAssignmentInstruction.scope` | `user`, `org` | Field owner: user AOP or linked org AOP. list-fields returns both; CRM mappings stay user-scoped. |

### createAop

| Parameter | Type | Required | Details |
| --- | --- | --- | --- |
| `name` | string | Yes | Name for the new AOP/playbook, e.g. "Deals - Brazil". minLength: 1 |
| `cloneFromAopId` | string | Yes | REQUIRED — the source user AOP id (your own, from read-playbook mode "list") to clone conversation/custom field definitions, display config, scope, icon, color, isNoOp, and the entire PLAYBOOK.md/resources/subagents document tree from. There is no from-scratch path. For a new PURE CLASSIFICATION bucket (a "Personal" category, another Spam-like filter, ...) with no automation at all, clone from an EXISTING no-op AOP (hasPlaybook: false, isNoOp: true in read-playbook mode "list" — e.g. Spam, Recruiting) rather than a live playbook AOP: the new AOP inherits isNoOp: true and, since the no-op source has no document tree, needs none either — do not try to clone a live AOP and strip it down.  |
| `selectionProcedure` | string | Yes | The new AOP's routing text — what an LLM classifier reads to decide a new conversation belongs here rather than the source AOP or any other. minLength: 1 |
| `scope` | "user" · "org" | No | Conversation ownership scope: "user" (one conversation per user+company) or "org" (one shared conversation per org+company). Defaults to the source AOP's own scope.  |
| `targetUserId` | string | No | Org owner/admin only: target a same-org member. Omit for self; non-admins and cross-org targets are rejected.  |

### updateSelectionProcedure

| Parameter | Type | Required | Details |
| --- | --- | --- | --- |
| `scope` | "user" · "org" | Yes | Field owner: user AOP or linked org AOP. list-fields returns both; CRM mappings stay user-scoped.  |
| `aopId` | string | Yes | The user AOP id (scope="user") or org AOP id (scope="org") whose routing text to replace.  |
| `selectionProcedure` | string | Yes | The full replacement routing text. REPLACES the existing text entirely, not a patch. minLength: 1 |
| `targetUserId` | string | No | Org owner/admin only: target a same-org member user AOP (scope=user). Omit for self; non-admins and cross-org targets are rejected.  |

### updateCustomAssignmentInstruction

| Parameter | Type | Required | Details |
| --- | --- | --- | --- |
| `scope` | "user" · "org" | Yes | Field owner: user AOP or linked org AOP. list-fields returns both; CRM mappings stay user-scoped.  |
| `aopId` | string | Yes | The user AOP id (scope="user") or org AOP id (scope="org") whose assignment instruction to replace.  |
| `customAssignmentInstruction` | string or null | Yes | Free-text org-specific guidance appended into this AOP's domain/company-identification prompt, overriding the model's own judgment (e.g. "never treat a known vendor/TPA/recordkeeper as the deal's customer; the real customer's name typically appears in the deal title"). REPLACES the existing text entirely, not a patch. Pass null to clear it back to no override. A scope: "org" write takes effect for any user AOP under it that has no instruction of its own set, and seeds any AOP cloned afterward — it does NOT retroactively overwrite a user AOP that already has its own instruction set directly.  |
| `targetUserId` | string | No | Org owner/admin only: target a same-org member user AOP (scope=user). Omit for self; non-admins and cross-org targets are rejected.  |
