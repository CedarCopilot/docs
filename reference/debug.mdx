<Accordion title="Full tool behavior and constraints">

For "why didn't X happen" questions, call load-skill('cedar-configuration') first — these actions surface raw signals, not an explanation of how integrations/playbooks/execution fit together. Debugging &amp; account-health ops, self-scoped by default (admin/owner: also a teammate in-org; staff: any account). ACTIONS: (1) diagnose-conversation — checks on a conversation (wrong company, vendor email contamination, missing AOP, failed executions). (2) recent-executions — recent agent executions for a conversation/user, or pass runId to drill into its tool calls. (3) execution-detail — one run's output/tool calls + each sub-agent it called (output, agentName, toolCallCount) but NOT their own tool calls — re-call with a sub-agent's runId for those. (4) tool-call-detail — full input/output for one tool call by id (from execution-detail's toolCalls&#91;&#93; or a sub-agent run's own calls). (5) health-report — per-user snapshot (targetUserId, defaults to yourself; admin/owner: also a teammate) OR org-wide status (orgId, Cedar-staff only) — the org-wide view skips an expensive red-flag signal the per-user view computes; never call an account healthy from it alone. (6) create-monitor — Sherlock verification/regression monitor. Cedar-staff only. (7) test-run — run a subagent you just authored/edited to see what it does before it ships. Self-scoped to your own agents + org-level agents your AOP links to. Sends suppressed by default (deliverForReal: false) — blocks sends only; DB and connected-system (CRM, Drive) writes still happen, so it is NOT a dry run. deliverForReal: true actually sends; on an org-level agent this needs org admin/owner. Each action's params go in a same-named object (e.g. action: "diagnose-conversation" pairs with diagnoseConversation: &#123;conversationId&#125;) — omit every object except the one for your action.

</Accordion>

## Operations and scopes

| Action | Capability | Baseline scope |
| --- | --- | --- |
| `diagnose-conversation` | Inspect a conversation's supported diagnostic state and processing evidence. | `crm:read` |
| `recent-executions` | Find recent agent executions with supported filters. | `crm:read` |
| `execution-detail` | Inspect a selected run's execution details and trace context. | `crm:read` |
| `tool-call-detail` | Inspect a recorded tool call's detailed input/output evidence where authorized. | `crm:read` |
| `health-report` | Read the supported account or execution-health report. | `crm:read` |
| `create-monitor` | Create the supported diagnostic monitor; requires the staff-only internal scope. | `internal` — staff only |
| `test-run` | Run one configured agent deliberately; sends are suppressed by default, but other writes can still occur. | `crm:read` |

Path, account role, feature gates, target ownership, and billing permissions can impose additional requirements.

## Supported options and filters

Every finite input choice is listed here, including array values and nested variants. Free-text filters, dates, numeric ranges and runtime validation are covered in the [parameter tables](/reference/debug#parameters). Options apply to their named operation or branch.

| Input | Choices | Variant / meaning |
| --- | --- | --- |
| `testRun.triggerType` | `cron`, `before_meeting`, `webhook` | "cron" fires exactly ONE named subagent in isolation (requires subagentName). "before_meeting" fires EVERY before-meeting subagent wired to conversationId — not isolated to one subagent, since Cedar has no isolated-single-agent before_meeting path today; this mirrors what a real meeting trigger actually does. "webhook" fires one registered webhook (requires webhookId) through the same dispatch path a real inbound POST or Slack-channel message would take — conversationless, so save-draft/save-slack-draft/task creation are unavailable to whatever it runs. |
| `testRun.level` | `user`, `org` | cron only. "user" reads the subagent from your own AOP; "org" reads it from the org AOP linked to your own AOP (you can only test an org-level agent your own AOP is actually linked to, never an arbitrary other org's). |

### diagnoseConversation

| Parameter | Type | Required | Details |
| --- | --- | --- | --- |
| `conversationId` | string | Yes | Conversation to diagnose. Self-scoped: the conversation must belong to your own org unless you are Cedar staff. format: "uuid" |

### recentExecutions

| Parameter | Type | Required | Details |
| --- | --- | --- | --- |
| `conversationId` | string | No | List executions for this conversation. Self-scoped: the conversation must belong to your own org unless you are Cedar staff. format: "uuid" |
| `targetUserId` | string | No | List executions for this user instead of a conversation. Defaults to yourself. Any-account if you are Cedar staff, or a teammate's if you are an org admin/owner in their same organization — a plain member passing a different user's id is rejected.  |
| `runId` | string | No | Drill into one run's tool calls instead of listing executions (takes priority over conversationId/targetUserId). Self-scoped by default: the run must belong to you, unless you are Cedar staff or an org admin/owner viewing a teammate's run in your own organization.  |
| `limit` | integer | No | Max executions to return, max 50 (ignored in runId mode). default: 10; minimum: 1; maximum: 50 |

### executionDetail

| Parameter | Type | Required | Details |
| --- | --- | --- | --- |
| `runId` | string | Yes | Run ID to fetch the full debug dump for (execution row, tool calls, sub-agent executions). Self-scoped by default: must be your own run, unless you are Cedar staff or an org admin/owner viewing a teammate's run in your own organization.  |

### toolCallDetail

| Parameter | Type | Required | Details |
| --- | --- | --- | --- |
| `toolCallId` | string | Yes | The `id` of one specific tool call (from execution-detail's toolCalls&#91;&#93; or subAgents&#91;&#93;) to fetch full input/output for. Use this to inspect a sub-agent's own tool calls — execution-detail's subAgents&#91;&#93; lists each sub-agent run but not its tool calls; drill into that sub-agent's own runId via execution-detail first to get its tool-call ids, then call this action per id.  |

### healthReport

| Parameter | Type | Required | Details |
| --- | --- | --- | --- |
| `targetUserId` | string | No | Per-user health snapshot for this user (meetings, tasks, agent-execution buckets, derived red/yellow issues). Defaults to yourself. Any-account if you are Cedar staff, or a teammate's if you are an org admin/owner in their same organization. IMPORTANT: this per-user view computes a "post-meeting pipeline degraded" red-flag signal that the org-wide view (pass orgId instead) deliberately skips because it is too expensive to run for every user in an org — always trust THIS view over the org-wide one when you need an authoritative read on one specific account.  |
| `orgId` | string | No | Org-wide health snapshot (green/yellow/red status per user in the org) instead of one user's detail. Cedar-staff only. IMPORTANT: this view does NOT compute the post-meeting-pipeline red-flag signal the per-user view (targetUserId) does — a user can show green/yellow here but red when the same action is called again scoped to just that user. Do not report an account as healthy based on this view alone; drill into targetUserId for any account that had recent meetings.  |
| `lookbackDays` | integer | No |  default: 7; minimum: 1; maximum: 90 |
| `orgAopId` | string | No | Per-user mode only: filter tasks/executions to AOPs under this org_aop_id.  |

### createMonitor

| Parameter | Type | Required | Details |
| --- | --- | --- | --- |
| `targetUserId` | string | Yes | The user account this monitor watches.  |
| `orgId` | string | No | Org this monitor belongs to, if applicable.  |
| `monitorType` | string | Yes | A slug describing the monitor kind, e.g. "regression", "reinvestigate", "config_verification". Not a DB enum — free text.  |
| `triggerConfig` | object | Yes | Must include `verify_condition` (a plain-English condition the evaluator checks against each new execution) — omitting it makes every future evaluation return "uncertain" instead of ever passing or failing; createMonitor() rejects a call missing it. Conventional keys used by the cedar-configuration skill's config-verification monitors: symptom_class, change_description, verify_condition, original_report, target_executions, event_type_filter.  |
| `alertChannel` | string | No | Slack channel or DM to alert when the monitor fires or resolves.  |
| `investigationId` | string | No | Ties this monitor to an existing Sherlock investigation row. Omit for monitors not tied to one (e.g. cedar-configuration config-verification monitors).  |

### testRun

| Parameter | Type | Required | Details |
| --- | --- | --- | --- |
| `triggerType` | "cron" · "before_meeting" · "webhook" | Yes | "cron" fires exactly ONE named subagent in isolation (requires subagentName). "before_meeting" fires EVERY before-meeting subagent wired to conversationId — not isolated to one subagent, since Cedar has no isolated-single-agent before_meeting path today; this mirrors what a real meeting trigger actually does. "webhook" fires one registered webhook (requires webhookId) through the same dispatch path a real inbound POST or Slack-channel message would take — conversationless, so save-draft/save-slack-draft/task creation are unavailable to whatever it runs.  |
| `subagentName` | string | No | cron only. The subagent slug to run, in isolation. Required unless agentId is given instead — provide exactly one of the two.  |
| `agentId` | string | No | cron only. Alternative to subagentName: the Agent Workspace agent_id (as shown in the UI, not the document filename). Resolved to its underlying &#123;aopId, subagentName&#125; before running — with targetUserId, this is how an admin runs a teammate's SAVED agent without already knowing its filename. Requires targetUserId when naming an agent that is not your own.  |
| `level` | "user" · "org" | No | cron only. "user" reads the subagent from your own AOP; "org" reads it from the org AOP linked to your own AOP (you can only test an org-level agent your own AOP is actually linked to, never an arbitrary other org's). default: "user" |
| `aopId` | string | No | cron only. Your own AOP id. Omit to auto-resolve when you have exactly one AOP; required if you have more than one.  |
| `conversationId` | string | No | Required when triggerType is "before_meeting". Self-scoped: must be a conversation you own. format: "uuid" |
| `webhookId` | string | No | Required when triggerType is "webhook". Must be a webhook registered to yourself (or, with targetUserId, to the teammate you are testing).  |
| `webhookPayload` | any | No | webhook only. Explicit payload; omitted defaults to `&#123;&#125;`.  |
| `deliverForReal` | boolean | No | Default false: outbound sends (Slack/email/notifications) are suppressed and this returns a preview of what WOULD have been sent. It is NOT a dry run: DB writes (tasks, fields, documents) AND writes to connected systems the agent makes itself (e.g. a HubSpot PATCH through run-code-executor, a Drive edit) still happen. To test without touching a CRM, use the agent's own read-only mode. Set true to actually deliver for real — for an org-level cron agent (level: "org") this requires you to be an org admin/owner, since it posts to a channel your whole team may share; a user-level agent only ever touches your own destinations, so no extra check applies there. default: false |
| `targetUserId` | string | No | Test-run this specific teammate's own subagent instead of yours — their AOP, their conversation ownership, their execution history. Defaults to yourself. Any-teammate only if you are an org admin/owner in the same organization as them; a plain member naming someone else is rejected.  |
