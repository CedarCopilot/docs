## Capabilities

[Notifications overview](/channels/notifications) · [Complete capabilities](/capabilities/notifications).

<Accordion title="Full tool behavior and constraints">

Send proactive notifications and discover Slack destinations. ACTIONS: (1) send — send a message to the user on the ONE channel they have chosen: Slack DM or channel (with structured Block Kit buttons — kind: action, link; style: primary, danger, default — reactions, and thread replies), iMessage (with tapbacks — emoji: thumbsup, thumbsdown, heart, haha, exclamation, question), email, or WhatsApp. Use for post-meeting DMs, daily agenda, alerts, and other out-of-band messages — NOT for the in-conversation reply, which uses the &lt;final_answer&gt; JSON pattern instead. Leave `channel` unset to use the user setting; set it (e.g. "email") only when the message argues for a channel — a long written report reads better in the inbox. Never use draft-comms to route a notification around a failed channel; that is for customer-facing mail. (2) list-slack-channels — list Slack channels (plus the user DM) accessible to the user. Call this before send with a slack.channelId destination to discover valid channel IDs. Each action takes its params in a same-named object (e.g. action: "send" pairs with a send: &#123;text, ...&#125; object) — omit every params object except the one matching your chosen action.

</Accordion>

## Operations and scopes

| Action | Capability | Baseline scope |
| --- | --- | --- |
| `send` | Send a user notification on the chosen configured channel, with supported Slack interactions or iMessage tapbacks. | `crm:read` |
| `list-slack-channels` | Discover accessible Slack notification destinations and the user's DM. | `crm:read` |

Path, account role, feature gates, target ownership, and billing permissions can impose additional requirements.

### send

| Field | Type | Required | Details |
| --- | --- | --- | --- |
| `presentation` | object | No | For background notifications supply presentation &#123;type, company?, person?, summary&#125; and why &#123;reason, instructionPaths?&#125;. Use verified names and one short source-grounded summary; Cedar owns the header and Why / change this button. Put full prep/details in slack.threadReplies. Keep internal IDs in hidden task/source context, never visible prose; use verified descriptive source links. No raw IDs. Use plain language and descriptive verified links; never invent URLs. For saved output pass its returned taskId. Preserve drafting eligibility, destinations and custom content. Do not invent a draft, contact, source URL or reason. | `why` | object | No |  |
| `taskId` | string | No | Exact saved task ID when notifying about task output. Its current owner and Task View notification policy are verified; omit for general notifications. format: "uuid" |
| `text` | string | Yes | Delivered to the user's chosen notification channel (Slack, email, iMessage, or WhatsApp). |
| `channel` | `email` · `slack` · `imessage` · `whatsapp` | No | Deliver on a specific channel instead of the user's default. Leave UNSET almost always — the user picks where their notifications land. Not a retry mechanism: a failed send already falls back to email on its own. |
