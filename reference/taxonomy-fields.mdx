<Accordion title="Full tool behavior and constraints">

The org's sub-event sales-taxonomy field DEFINITIONS — the extraction schema behind the deal-intelligence data (objections, discovery questions, pain, demo moments, MEDDPICC signals, rep tactics). These are ORG-level extraction config and deliberately do NOT appear in a deal's CRM columns, so this tool is the only way to learn they exist. CALL THIS FIRST whenever a question is about what happened INSIDE calls or emails (what objections come up, which questions reps ask, how often X is mentioned, what separates won from lost) — it tells you which fields exist, which plane each stores on, which carry strength/completeness scores, which payload keys you can group by, and the org's stage vocabulary (raw CRM stage values are opaque ids). ACTIONS: (1) list — the whole catalog, one line per field, plus stageVocabulary. (2) get — one field in full: its extraction prompt (what the extractor was actually asked for), scoring rubrics, metadata sub-fields and seeded vocabulary. Definitions only; for the extracted VALUES use run-sql, conversation-read or conversation-analytics.

</Accordion>

## Operations and scopes

| Action | Capability | Baseline scope |
| --- | --- | --- |
| `list` | List the gated taxonomy field catalog for the account. | `brain:read` |
| `get` | Inspect a selected taxonomy field's definition and evidence structure. | `brain:read` |

Path, account role, feature gates, target ownership, and billing permissions can impose additional requirements.

## Parameters

| Parameter | Type | Required | Details |
| --- | --- | --- | --- |
| `action` | "list" · "get" | Yes | list = the org's whole taxonomy catalog (one compact line of shape per field); get = one field in full, including its extraction prompt, scoring rubrics and payload keys.  |
| `fieldId` | string | No | Required for action "get" — the field id from `list`, e.g. "objection.raised".  |
| `aopId` | string | No | Optional: restrict to one org playbook (AOP) when the org runs more than one taxonomy set. Omit for all of them — most orgs have exactly one.  |
| `user_request_summary` | string | Yes | One sentence, in your own words: what the user actually asked you to do in this turn. Used only for Cedar's observability — it does not change what this tool does.  |
| `is_new_request` | boolean | Yes | true on the FIRST Cedar tool call of a NEW user request; false when this call continues the same request you are already working on. Groups related calls into one activity thread.  |
